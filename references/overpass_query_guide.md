# Overpass 查询指南

`scripts/query_overpass.py` 已经把查询逻辑封装好了，这里只说明**怎么选参数**和
**怎么解读返回结果**，不需要手写 Overpass QL。

## 半径怎么选

基础查询半径应该基于 `geo_stats.py` 算出的地块尺寸，而不是固定 300 米：

```
radius_m = max(150, 0.6 * max(bbox_width_m, bbox_height_m))
```

如果前一轮查询没有直接项目名称/项目编号/“在建”等线索，可以将该基础半径临时扩大到
**2–3 倍**做一次“项目证据补查”。扩大范围的目标是捕获临近主干道、地块边界外的项目 POI
或反向地理编码线索；扩大查询结果不能自动视为地块本身的直接证据。

- 小地块（单栋楼、几千㎡）：150–300 米足够覆盖周边街区
- 大地块（园区、大型小区，几万㎡以上）：按上面公式放大，避免查询范围只覆盖到
  地块内部、查不到周边参照物
- 线状地物（道路、管线）：以整条线的中点或多个采样点分别查询，半径可以小一些
  （100–150 米），重点看沿线 `highway` 名称和沿线 POI

## 结果怎么解读

返回 JSON 的五个字段，重要性从高到低：

1. **landuse** — 最直接的证据。如果非空，`region_type` 判断应该以此为主要依据，
   参照 `landuse_taxonomy.md` 里的映射表。
2. **buildings.by_type** — 建筑类型分布（如 `{"apartments": 8, "yes": 4}`）。
   `apartments`/`house` 强烈指向住宅；`industrial`/`warehouse` 指向工业/仓储；
   `commercial`/`office` 指向商业。`yes` 是通用建筑标签，信息量低，不要过度解读。
3. **amenities** — 具体设施点（学校、医院、商铺等），对判断"可能建筑"和"相关
   项目"很有用，尤其是带 `name` 的条目可以直接作为候选建筑名称的参考。
4. **roads** — 道路名称，主要用于地址描述和辅助判断区域等级（主干道 vs 巷道），
   不单独作为区域类型的证据。
5. **places** — 如果命中了 `place=suburb/neighbourhood` 等标签且带 `name`，
   这通常是该区域的官方或通用地名，可以直接用于描述"这是什么区域"。

## 空结果怎么办

如果五个字段全部为空数组/零计数，说明该区域 OSM 数据覆盖不足（常见于新建区域、
农村地区），此时：

- 不要把"OSM 无数据"当作"这里没有建筑/是空地"的证据
- 明确标注 `data_source` 为 `offline`，转为依赖 `geo_stats.py` 的形状特征和
  `properties` 里的原始字段做弱证据推理
- `region_type`/`possible_buildings`/`related_projects` 里对应给出较低置信度
  （建议不超过 0.4），并在 evidence 里写明"OSM 无覆盖数据，基于几何形状推测"

## 批量查询时的礼仪

- 每次调用之间建议 `sleep(1)` 左右，避免对公共 Overpass API 造成压力
- 单次批处理超过约 50 个地物时，考虑改用一次性的 bbox 查询覆盖所有地物范围，
  而不是逐个调用（可以在这个基础上后续扩展一个 `query_overpass_bbox.py`，
  当前版本先满足单点/少量地物场景）
- 网络失败（脚本退出码 2）不要重试超过 1 次，直接转离线模式，避免用户长时间
  等待
